## 0. 目的（改善策ではなく因果の検定）

0b 裁定 §2 の留保をそのまま引き継ぐ。O3 は改善策としてではなく、
**L1（最適化衛生）が基礎劣化の原因かを検定する対照実験**として登録する。

検定したい命題:

> **H(O3): 1 バッチあたりの最適化量（epoch 数）の削減は、PPO が init の基礎技能
> （放銃回避）を劣化させる度合いを小さくする。**

O1 は「データの鮮度」を、O3 は「同じデータを何回舐めるか」を触る。
**O1 は H を支持しなかった**（放銃 z=+4.91、baseline 比 −0.32 z = n.s.）ので、
L1 仮説の残りの主要な足はこの O3 になる。

## 1. 介入定義（単一変数）

`[ppo] ppo_epochs = 4 → 1`。**config 1行。学習コード・libriichi・eval 経路すべて無変更。**

`mortal/train_ppo.py:490` の `for epoch in range(ppo_epochs)` が回る回数が変わる。
`minibatch_size = 512` は全 run で一度も効いていない（バッチ median 168–179、
`ppo_optimization_health_20260725.md` 事実1）ので、実体は:

| | 1 バッチあたり optimizer step | 16000 step の総勾配更新 | 消費半荘数 |
|---|---:|---:|---:|
| base（`=4`） | 4 | 64,000 | 16,000 |
| **O3（`=1`）** | **1** | **16,000** | **16,000** |

`steps += 1` はバッチ単位（epoch ループの外、`train_ppo.py:592`）なので、
**16000 step の消費データ量は base と同一**。判定窓を step 基準のまま使える
（O2 と違い batch 束ねをしないため。`robust_selfplay_ppo_design.md` §2a の罠を踏まない）。

### 1a. この変数が実際に動かす量（**新規実測**）

`ppo_diag.jsonl` の `ppo_epoch` イベントから epoch 別の trust region 指標を集計
（step ≥ 500、5 run）:

| run | clip@e1 | clip@e4 | ratio_mean e1→e4 | ratio_std e1→e4 |
|---|---:|---:|---|---|
| stage1_resume | 0.2019 | 0.2006 | 0.9996 → 0.9992 | 0.2095 → 0.2069 |
| stage3 | 0.2132 | 0.2119 | 0.9999 → 0.9995 | 0.2044 → 0.2020 |
| anchor_k | 0.2142 | 0.2127 | 1.0001 → 0.9996 | 0.2100 → 0.2073 |
| b04 | 0.2059 | 0.2043 | 1.0001 → 0.9997 | 0.2028 → 0.1999 |
| l1_o1 | 0.2046 | 0.2030 | 1.0000 → 0.9996 | 0.2047 → 0.2020 |

- **epoch 2–4 は「バッチ内で方策をほとんど動かしていない」**: `ratio_mean` は
  4 epoch を通じて 0.999–1.000 のまま（変化 ≤0.0005）、`ratio_std` の変化も
  −0.0024〜−0.0029（**約 1%**）。**符号は 5 run すべてで一致**（epoch を重ねると
  ratio の散らばりがわずかに縮む = 現方策が挙動方策側へ寄る）
- clip@epoch1→epoch4 の差も −0.0013〜−0.0016 で、`ppo_optimization_health_20260725.md`
  事実3（−0.0008〜−0.0032）を 5 run で再確認
- **⇒ epoch 2–4 を落としても「バッチ内の trust region 占有」はほとんど変わらない。**
  epoch 2–4 が clip を減らす機能を果たしていない以上、O3 が clip 経由で効く筋は薄い

> ⚠ **にもかかわらず O3 は小さい介入ではない。** 上表は「1 バッチ内で見た方策の動き」で
> あって、**epoch 2–4 は全 optimizer step の 75% を占める**。バッチ内で測れる動きが小さくても、
> 16000 バッチ分を積み上げた総移動量は別物。**O3 は「trust region の衛生」と
> 「総最適化量 1/4」を同時に動かす**（§8-1 が本実験の最大の留保）。

### 1b. 事前予測を置かない量

O1 §1b と同じ理由で、**clip_fraction・劣化幅の量級について事前予測は置かない**。
上の §1a は「clip 経由の筋は薄い」と言えるだけで、総最適化量の経路がどう効くかは
較正情報がない。数値予測を置くのは Stage3 v1 の較正ミスと同型なので採らない。

### 1c. スループットへの影響（**新規実測**）

trainer.log の timestamp から epoch 2–4 の所要を実測:

| run | epoch2–4 の所要 | step 間隔 median | 占有率 |
|---|---:|---:|---:|
| l1_o1 | 0.966s | 1.491s | 64.8% |
| anchor_k | 0.893s | 1.417s | 63.0% |
| b04 | 0.883s | 1.418s | 62.3% |

- **trainer 計算としては 63–65% 削減**だが、**wall clock は client 律速**
  （O1 実測 27.6h / 16000 step = **6.21 s/step** に対し step 間隔 median は 1.49s
  = trainer はほとんどデータ待ち）。
- ⇒ **run 時間はほぼ変わらない見込み（24–28h）**。大幅に短くなった場合は
  「trainer 律速だった」という別の事実の発見なので §12 に記録する。

## 3. 判定条件（**凍結。以後変更禁止**）

**O1（および anchor C/K/b04）と完全に同一の計測器・同一 seed・同一 n**。
すべて step16000 checkpoint、1v3 grp_baseline、argmax / guard ON / 自然分布、
`analyze_fundamentals_1v3.py`、両脚 n=800 半荘（seeds [10000,10200)）。

1. **主判定1（基礎維持）**: 放銃率(ckpt) − 放銃率(init) が半荘クラスタ robust SE で **z < 2**
2. **主判定2（経済適応の保持）**: チップ/半荘 (ckpt − init) が **+方向 かつ ≥1SE**
3. **副次（判定外・記録のみ）**:

   - clip@epoch1 と ratio（epoch は1つしかないので epoch 間比較は消える）

   - 有役テンパイ機会の見送り率・向聴を外した率（`policy_quality_metrics_20260728.md`）

### 3a. 「壊れなかった」と「動かなかった」を識別する副次指標（**事前登録**）

§8-1 の交絡（総最適化量 1/4）への対処。**放銃劣化が小さかった場合に、それが
「衛生が効いた」のか「単に学習が進まなかった」のかを分ける**ために、
**init からの行動シフト量**を併記する（すべて既存の eval 出力から取れる。新規測定なし）:

| 指標 | init | 参照 Stage1-16000（`=4`） |
|---|---:|---:|
| 立直率 | 24.27% | 38.93% |
| 副露率 | 17.33% | 6.47% |

読み方（**結果を見る前に固定する**）:

| 放銃劣化 | 行動シフト量 | 読み |
|---|---|---|
| 小さい | **参照と同程度** | **H(O3) 支持**（同じだけ動いたのに壊れていない = 衛生の効果） |
| 小さい | **参照より明らかに小さい** | **交絡が支配**（単に学習が進んでいない）。H(O3) の証拠にならない |
| 参照と同程度 | 参照と同程度 | **H(O3) 不支持** |

「明らかに小さい」の操作的定義: **立直率シフトと副露率シフトの両方**が
参照の変化幅（それぞれ +14.67pp / −10.86pp）の **1/2 未満**であること。

## 8. 留保（結果の読みに必ず添える）

1. **交絡: O3 は 2 つのものを同時に動かす（最重要）**。
   (a) バッチ内の trust region 占有（§1a より、ほぼ動かない）と
   (b) **総勾配更新回数 64,000 → 16,000**。
   したがって「劣化が減った」が観測されても、それが最適化衛生の効果か
   **単に方策が init から遠くへ行かなかっただけ**かは、この 1 run だけでは決まらない。
   **§3a の識別指標を必ず併記する**（それでも完全な分離ではない）。
   完全な分離には lr 補正など第2の変数が要り、それは別実験（1 branch = 1 variable に反する）
2. **run 間ばらつき**: 同一 config の run 間ばらつきは効果量と同程度
   （`early_damage_probe_result_20260729.md` §9）。**この 1 run で判定1 の閾値を跨ぐか否かを
   決める検出力は限定的**。だから §5 の逐次スクリーニングを掛ける。cross-run 比較（§6）はさらに弱い
3. **eval SE は保守的**（`check_cluster_se.py`。seed クラスタ + 両脚対応で 0.77–0.81 倍）。
   判定値は現行 SE で出す。結論は「少なくともこの強さ」と読む
4. **O1 と O3 は独立ではない**: どちらも「最適化衛生」という 1 つの仮説族の別の足。
   両方 ✗ でも L1 の全候補（O2/O4/O5）を否定はしない
