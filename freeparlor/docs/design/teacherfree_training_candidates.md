## 0. 出発点 — 「教師データを使わずに1から」は2つの別問題

ブレストの発端は「天鳳牌譜で学習するフェーズを、自己対戦 + 人間ラベリングで
代替できないか」という問いだった。議論の過程で、この問いが**2つの独立な問題を
混同している**ことが判明した。この分離が本書の組織化の軸である（同じ混同を
繰り返さないために記録する）。

| # | 問題 | 内容 | 現状 |
|---|---|---|---|
| **I** | **cold start** | 乱数初期化のネットワークに麻雀の盤面を「読める」ようにさせる。本家 Mortal が天鳳鳳凰卓の牌譜（数億判断オーダー）で担っていた役割の大部分は、人間の正解行動の模倣ではなくこの表現学習 | 本プロジェクトは mortal 重み（`beta1_huber_192x40`）を init に使っており、**この問題を回避してきた**。商用版はゼロ実装なので回避できない |
| **II** | **均衡脱出** | 自己対戦が「立直マキシマリズム」という単一均衡へ収束し、鳴き・カンといった低確率行動が絶滅して再評価されない | 探索ラダー3段（Stage1 純探索 0.236× / Stage2 分布介入 0.185× / Stage3 報酬介入 1.066×・slope/SE=−21.03）が**全段不成立**で閉幕。DRCA が「絶滅した行動に実際どれだけの EV があるか」を測定中 |

候補と問題の対応（詳細は §1 の表）: 候補1 は問題 I、候補2・3 は問題 II、
候補4 は両方、候補5 は横断。**当初の HITL 案は問題 I を解こうとして問題 II の
解法（介入 → 撤去 → 回帰）を再演してしまう構造**になっていた（§6a）。

## 2. 候補1: シミュレータ由来の自己教師あり補助タスク（問題 I の最有力）

共有エンコーダに補助予測ヘッドを生やし、自己対戦データ上で「盤面についての事実」を
予測させる。方策ヘッドには行動を一切教えない。ラベルは全て libriichi が無料で
厳密計算できるので、人手ゼロでスケールし、人間バイアスも入らない。

### 2a. 何を予測させるか

| 予測対象 | ラベルの型と値 | 正解の出所 | 既に obs v4 の入力にあるか（§2b） |
|---|---|---|---|
| 自手のシャンテン数 | 整数 0–6 の7クラス分類 | シャンテン計算器 | **ある** |
| 受け入れ | 打牌候補ごとの「切った後の受け入れ枚数」ベクトル（回帰） | 全候補の機械的列挙 | **ある**（打牌別の有効牌 bitmap） |
| 聴牌到達確率・和了確率・巡目別 EV | 打牌候補 × 巡目の実数 | 単騎計算機（`algo/sp`）の厳密列挙 | **ある**（3 × 17 巡） |
| 危険牌 | 34種それぞれに 0/1（今切ったら誰かにロンされるか） | 全員の手が見えるので厳密解 | **ない**（`waits()` から導出可能だが役の扱いは未検証） |
| 相手の聴牌状態 | 相手3人それぞれに 0/1 | 同上 | **ない**（oracle 側に計算済み） |
| 相手の待ち牌 | 相手ごとに34次元の 0/1 ベクトル | 同上（oracle 蒸留） | **ない**（oracle 側に計算済み） |
| 局の結末 | 和了者（4人 + 流局の5クラス）+ 自分の点数変動 | 局終了時点の実際の結果 | **ない**（結果ラベル） |

損失は分類なら cross-entropy、回帰なら MSE で、PPO 損失に小さい重みで足して勾配を
共有エンコーダへ流す。**ラベルは2種に分かれる**（性質が違うので混同しない）:

- **事実ラベル**（上の5つ）: 判断のその瞬間に厳密計算でき、**方策に依存しない**。
  「相手の待ちは 3-6p」は誰がどう打っていようが真実。dense で即座に正解が手に入り、
  バイアスの入りようがない。特に危険牌と相手の待ちは、プレイヤーから隠れている
  情報を当てさせる **oracle 蒸留**であり、「見えない情報の確率的推論」という麻雀の
  実力の本体をエンコーダに強制的に獲得させる
- **結果ラベル**（局の結末）: 局末まで正解が確定せず sparse、かつ「誰が和了るか」は
  全員の打ち方に依存するので**方策依存**。既存の GRP（最終順位予測器）がこのクラス。
  下手な自己対戦での結末予測から始まるが、方策が育つとラベル分布も育つので
  cold start の足がかりとしては問題にならない

### 2b. 重複監査 — 既に入力にあるもの / ラベルにしかできないもの（2026-07-25 調査）

一次ソース確認の結果、**自手側の事実は既に観測の入力に入っている**。
`libriichi/src/state/obs_repr.rs` の `version == 4` ブロックが単騎計算機
（`libriichi/src/algo/sp` の `Candidate`）の出力をそのまま特徴量として符号化しており、
PPO の全 run は `version = 4`（`freeparlor/configs/ppo_stage3.toml`）である。入って
いる中身は、打牌候補ごとの有効牌 bitmap（向聴戻しか否かで2面）、巡目ごとの聴牌
確率・和了確率・期待値（3 × 17 巡）、全体最大 EV、最大受け入れ打牌の指示。

したがって §2a のラベル群は marginal value で3層に並べ直すのが正しい:

| 層 | ラベル | 追加される情報 | ラベル化の価値 |
|---|---|---|---|
| 下 | 自手の事実（シャンテン・受け入れ・聴牌確率・EV） | **なし**（既に入力） | エンコーダに保存を強制する錨としてのみ。「π ヘッドの仕事が結線に縮む」効果はこの層では弱い |
| 中 | 局の結末（結果ラベル） | 既存 GRP の拡張 | 中（critic の立ち上がりに効く） |
| 上 | **隠れ情報の oracle**（相手の待ち・聴牌・危険牌） | **入力に無い情報そのもの** | **最大**。「見えない情報の確率的推論」を強制できる唯一の層 |

この監査を経ると、候補1 の実体は「補助タスク一般」ではなく **oracle 蒸留が本体**で
あると言い直せる（§2f のとおり oracle テンソルは既に計算済みで、実装差分は「入力では
なくラベルとして使う」だけ）。cold start での「盤面が読めない」の中身も、自手の
牌効率ではなく**隠れ情報の推論**の側にあると解釈するのが一次ソースと整合的である。

### 2c. なぜ行動ラベルではないのか

「シャンテン数が下がる打牌に正解ラベルを与える」「受け入れ枚数が多い打牌を正解に
する」は**行動への教師信号**であり、牌効率マキシマリストというルールベースの先生を
注入したことになる。人間牌譜と同種のバイアスであり、しかも降りを知らない分だけ
人間より偏っている。「人間らしさ不要・人類が思いつかなかった打ち方も歓迎」という
本プロジェクトの目標（`policy_session_0b_frame.md` 議題1 の前提）と真っ向から衝突する。

補助タスクが与えるのは**状態についての事実**のみである。「シャンテン数を予測できる」
ことと「シャンテン数を最小化する」ことは別物で、シャンテン戻しが正解の局面でも
予測ヘッドは「今シャンテン数が上がった」と正しく認識するだけで、それを罰しない。
**認識と選択の分離**が本候補の核心であり、何が良い行動かは引き続き PPO（正典報酬）
だけが決める。

### 2d. 深さの設計軸 — Gamba の指標欠陥指摘は「入力の忠実度」に着地する

Gamba の指摘（2026-07-25）: シャンテン数と現在の受け入れ枚数は指標として欠陥がある。
シャンテン数を落とした方が後の打点・受け入れが増える場面が多々あり、受け入れ枚数も
5ブロック vs 6ブロックの議論（今の受け入れは6ブロックが多いが、1手進んだ時点の
受け入れは5ブロックが多い。だから基本5ブロックが強い）のように1手先だけ見ると誤る。

これは「シャンテン数を消せ」ではなく**「手変わり・向聴戻しを織り込んだ評価を使え」**
という要求である。そして一次ソースを見ると、**その能力は libriichi にあり、観測
エンコーダでは意図的に切られている**（2026-07-25 調査）:

`libriichi/src/state/agent_helper.rs` の `SPCalculator` 構築箇所は
`calc_tegawari: false`（手変わり考慮）・`calc_shanten_down: false`（向聴落とし考慮）で
計算している。`libriichi/src/algo/sp/calc.rs` の 234 行・590 行の分岐がこのフラグで
向聴戻し候補の列挙をゲートしており、同ファイルのライブラリ自身のテストは両方 `true`
で回している（おそらく CPU コスト由来の既定値）。深い局面向けの簡易解析
（`analyze_discard_simple`）では向聴戻し候補の受け入れ牌だけは列挙されるが、
**確率・EV を計算する本解析では評価対象から外れている。**

したがって Gamba の指摘は二段に分けて扱うべきである:

| 段 | 打ち手 | 内容 | コスト |
|---|---|---|---|
| **入力の忠実度** | SP 計算の2フラグ | `calc_tegawari` / `calc_shanten_down` を有効化し、手変わり・向聴戻しを織り込んだ確率・EV を観測に入れる | **候補1 より遥かに安い単一変数実験**（Rust の既存機能・ラベルもヘッドも不要。ただし CPU コストとスループットへの影響は要実測） |
| **ラベルの深さ** | 補助ヘッド | §2b の3層のうち上層（隠れ情報 oracle）を予測させる | 16k run 1本 |

深さの上側の境界線は不変である: 「この打牌の EV」まで行くと相手の行動に依存する
= Q(s,a) 本体であり、シミュレータが無料で厳密計算できる事実ではなくなる。そこから
先は RL（あるいは候補4 の探索）の仕事である。設計原則は**「厳密に列挙計算できる
範囲で、できるだけ深い量」**のままで、単騎計算機の2フラグはその範囲の内側にある。

### 2e. 人間ドメイン知識の投入口

「何を予測させるか」の設計は、価値判断のバイアスを持ち込まずに Gamba のドメイン知識を
投入できる唯一の場所である。Gamba が「自分が何を根拠に打牌を選んでいるか」を言語化し、
出てきた各根拠を次の3分類に仕分ける:

1. **シミュレータが厳密計算できる事実か**（2手先受け入れ、現物・スジ状況、山に残って
   いる枚数など）→ そのまま補助タスクの予測対象に採用
2. **隠れ情報についての推論か**（あの捨て牌なら染め手っぽい等）→ oracle 蒸留の
   予測対象に採用（正解 = 実際の相手の手）
3. **価値判断か**（ここは打点より速度、等）→ **採用しない**。RL が正典報酬から
   自力で見つけるべき領域で、ここに入れた瞬間バイアスになる

1 と 2 が多いほど cold start が楽になる一方、雀力の一番おいしい部分（3）はあえて
捨てる構造になる。それで正しい — 3 を注入しないからこそ、人類が思いつかなかった
打ち方の余地が残る。**人間は問題用紙を作り、シミュレータが模範解答を書き、
何点を狙うかは AI が決める**という分業。

### 2f. 既存資産と実装上の注意（2026-07-25 調査）

本候補の配線は**大半が既に存在し休眠している**。

| 資産 | 場所 | 現状 |
|---|---|---|
| 単騎計算機（SP）テーブルの観測符号化 | `libriichi/src/state/obs_repr.rs` の `version == 4` ブロック・`encode_sp_table`、`libriichi/src/algo/sp/candidate.rs` | **入力として稼働中**（§2b）。打牌別有効牌 bitmap 2面 + 巡目別の聴牌確率/和了確率/EV + 最大 EV |
| SP 計算のオプション | `libriichi/src/state/agent_helper.rs` の `SPCalculator` 構築（`calc_tegawari: false` / `calc_shanten_down: false`） | **意図的に無効**（§2d）。有効化は候補1 より安い別の単一変数実験になり得る |
| oracle 観測テンソル（相手3人の手牌・赤保持・シャンテン・待ち + 山/嶺上 index。PPO は `version = 4` なので 217×34、通常 obs は 1012×34） | `libriichi/src/consts.rs` の `oracle_obs_shape`、`libriichi/src/arena/board.rs` の `encode_oracle_obs`、`libriichi/src/dataset/invisible.rs` | 自己対戦 arena 側にも実装済み。`arena/game.rs` が agent の `oracle_obs_version()` を見て per-player に encode し `invisible_state` として渡す |
| agent 側のフック | `libriichi/src/agent/mortal.rs` の `oracle_obs_version()` → `self.is_oracle.then_some(version)`（`is_oracle` は Python engine 属性由来） | **Rust 変更ゼロで有効化できる**。現状は全 call site が `is_oracle=False`（`ppo_engine.py` 等）で休眠 |
| Python 側の受け口 | `mortal/engine.py`・`mortal/ppo_engine.py` の `react_batch(obs, masks, invisible_obs, ...)`、`mortal/dataloader.py` の `take_invisible_obs()` | 引数は既に通っている（`ppo_pool_engine.py` は `del invisible_obs` で破棄） |
| 補助ヘッドのパターン | `mortal/model.py` の `AuxNet`。使用例は `mortal/train.py`（`AuxNet((4,))` + 共有特徴 `phi` から最終順位を CE で予測） | **DQN 経路に前例あり**。PPO 経路（`train_ppo.py`/`ppo.py`）には補助ヘッドが一切ない |

**向きが逆であることに注意**: 本家 Mortal は `invisible_obs` を **encoder の入力**として
使う（`Brain(is_oracle=True)` が in_channels に連結する = oracle net を作って盲目 net へ
蒸留する方式）。本候補が必要とするのは**予測ラベル**としての同じテンソルである。
したがって実装時は「oracle obs を受け取る」ことと「encoder に食わせる」ことを
Python 側で分離する（`Brain` は `is_oracle=False` のまま、テンソルは補助ヘッドの
教師としてのみ使う）。

**規律**: oracle 経路は訓練専用であり、eval/配備経路に漏れてはならない。既存の
`p_enrich`・`call_bonus_b` と同じ「構成 dump に含めて検定で無効を assert」の規律を
敷くこと（`stage2_design.md` §2・`stage3_design.md` §7 の踏襲）。なお oracle を訓練手法
として試したことは本プロジェクトで一度もなく、`supervisor_handbook.md` §4b の
「殺した仮説」にも該当しない（`freeparlor/docs/` 内の言及は DQN 期のデータパイプライン
文書2本で、休眠経路としての記述のみ）。

### 2g. 限界・コスト・Stage3 との違い

- **コストは「損失に1項」では済まない**。補助損失は共有エンコーダを変えるので方策が
  変わる。1 branch = 1 variable の帰結として、評価には Stage 系と同じ 16k run 1本
  （≈2日 + drain 数百 GB。`run_artifact_retention.md` の保持運用に従う）と、同一 init・
  同一 config の対照が必要になる
- 序盤のデタラメ対局は「まともな麻雀では訪れない状態」ばかり訪問するので、そこで
  学んだ表現の一部は無駄になる。ただし事実ラベルは分布がどうであれ常に厳密なので、
  方策が育って状態分布がまともになれば表現も追随する。**教師データの「先生と生徒の
  分布ずれ」問題が構造的に存在しない**のが隠れた美点
- フェーズ分けは不要。step 0 から PPO と同時に回し（序盤は報酬信号が無意味でも
  補助損失は初手から濃密で正確なので、胴体だけが先に育つ）、主導権が自然に
  補助 → PPO へ移る。補助損失は**その後も切らない**（RL 中の表現崩れを防ぐ錨）
- **Stage3 の「anneal したら消える」問題は起きない**。あれは報酬（価値判断）への
  介入だったため撤去後に均衡へ回帰した。補助損失は価値判断に触れていないので、
  残し続けても打ち筋を歪めず、外しても「盤面を読む力」は重みに焼き付いたまま残る

## 3. 候補2: リーグ訓練・敵対的搾取者（問題 II・最も安い・検証兼用）

`policy_session_0b_frame.md` 議題3「敵対的搾取者訓練の要否」の粗設計に相当する。
AlphaStar（StarCraft II、2019）のリーグ構造の部品。

### 3a. 素朴な自己対戦の病理と搾取者の訓練手順

最新版の自分とだけ対戦し続けると、方策は「今の自分に勝てる打ち方」へ最適化される。
病理は2つ: (a) **じゃんけんの堂々巡り**（絶対的に強くなっていないのに自己対戦勝率
だけ上がる）、(b) **共進化の袋小路**（集団全員が同じ癖を持つと、その癖を咎める戦略に
誰も出会わないので癖が弱点として固定される）。立直マキシマリズムは (b) の疑いがある
— 「鳴かない打ち方」は**相手も全員鳴かない世界**での均衡かもしれない。

搾取者（main exploiter）の訓練:

1. 新品（または本体のコピー）として生まれる
2. **凍結した標的とだけ**対戦する。リーグの他の誰とも戦わない
3. 目的関数は普通の勝利報酬。ただし相手が1人に固定されているので、汎用的な強さでは
   なく「こいつ専用の攻略法」が最短経路になる（相手が固定なら癖を突くのが一番効率的
   だから、自然にそうなる）
4. 標的に一定勝率を超えたら**凍結してリーグに追加**し、自分は引退
   （次の搾取者が生まれる）

つまり搾取者は「本体の現在の弱点を自動発見する使い捨ての専門家」で、リーグに残ることで
「本体が二度と同じ弱点を持てない」ようにする装置。もう一つの部品 **PFSP**（優先架空
自己対戦）は、本体の対戦相手を一様ではなく**勝率の低い相手ほど高頻度で**選ぶ仕組み
（完封できる過去の自分と戦う時間を捨て、苦手な搾取者に訓練時間を集中させる）。

### 3b. うちへの写像

配管の大半は既にある。現行 PPO は challenger（学習中）vs champion プール（凍結
checkpoint 群）の 1v3 構造（`OneVsThree`・`opponent_pool`）で、リーグ訓練はこの
プールの中身と選び方を賢くするだけである。

1. **搾取者 run**: 新規 init を、凍結した Stage1-16000 の3体を相手に普通の PPO で回す。
   **正典報酬のみ・介入なし**（報酬汚染禁止・行動上書き禁止の禁則に一度も触れない）
2. 搾取者が標的に有意な差をつけたら凍結し、本体の champion プールに追加
3. **本体の継続訓練**: プール = {過去の自分たち + 搾取者たち}、負け越している相手を優遇
4. 2–3 を繰り返す

麻雀での期待シナリオ: 「絶対に鳴かない相手」への攻略法は例えば「手出しツモ切りから
立直だけケアすればよい（仕掛けのケア不要で押し引きが単純化する）」「赤を切っても
鳴かれない」など、人間のフリー雀荘でも実際に言われる搾取である。

### 3c. Gamba の懐疑と、どちらに転んでも情報になる構造

Gamba の懐疑（2026-07-25、記録する価値のある論点）: 「搾取者は、ただ立直が上手く
なっただけの AI になるのでは？」— **半分正しい**。勾配降下は創造性を保証せず、
目的関数の最短経路が「同じ立直麻雀をより精密にやる」ならそうなる。

しかし搾取者訓練の正体はゲーム理論の**ベストレスポンス演算の実行**であり、結果は
2つしかない:

| # | 結果 | 意味 |
|---|---|---|
| (a) | BR(立直マキシマリスト) = より上手い立直マキシマリスト | 立直マキシマリズムはベストレスポンスの不動点に近い = **搾取不能な頑健均衡**である証拠。「鳴かないのは自己対戦の錯覚では」仮説が棄却される |
| (b) | BR が質的に違う打ち方（仕掛けの活用、押し引き単純化の悪用など） | 均衡は錯覚であり、**搾取の存在証明**が取れる |

Gamba が心配しているのは (a) だが、それは実験の失敗ではない。ラダー各段と同じ
「どちらに転んでも知見になる」形をしている。

補足すべき事実: 既存の訓練は全て challenger を「mortal 的な相手のプール」と戦わせて
きた。つまり Stage1-16000 は**mortal 的な相手へのベストレスポンス**として育った方策で
あり、**完成した Stage1-16000 自身へのベストレスポンスは一度も計算していない**。
これが「自己対戦の錯覚」疑惑（`ppo_p3_stage1_result.md` の解釈限界、
`ppo_p3_stage3_result.md` §9「この均衡の外に、鳴きを使いこなす搾取者が存在するかは
未検証」）を晴らせていない理由であり、搾取者1体はその検算に当たる。

### 3d. 「ただ強くなった」vs「搾取」の操作的定義

搾取者が完成したら、2つの対戦成績を測る:

1. 搾取者 vs **標的**（訓練で狙った凍結 checkpoint）
2. 搾取者 vs **中立な相手**（init や別系統の checkpoint）

「ただ立直が上手くなっただけ」ならレート差は相手によらず一様に出る。**標的に対して
だけ不釣り合いに勝つ**なら標的固有の癖を突いている = 搾取の操作的定義。Gamba の懐疑は
設計段階で悩む必要のない、実験後に検証可能な仮説である（配備税を 2SE 検定で炙り出した
のと同じ流儀で白黒つく）。

### 3e. 事前登録すべき設計判断（本書では確定しない）

1. **判定条件**: §3d の「標的固有のレート差上乗せ」の有無を主判定にする
2. **搾取者の init**: 標的のコピーから始めるか（強いが同じ盆地に囚われやすい）、
   mortal init から始めるか（別の盆地を探索できるが立ち上がりが遅い。AlphaStar は
   後者寄りの再初期化で奇襲系を発見している）。**1 branch = 1 variable** に従い、
   まず1本どちらかに決め、結果を見てからもう片方

### 3f. 副産物と注意点

**副産物（AI の外でも価値がある）**: 搾取者が標的固有の攻略を見つけた場合、その中身は
牌譜に現れる。Stage1/Stage3 でやった専門家定性レビュー（`qualitative_expert_review_
20260715.md`・`qualitative_expert_review_stage3_20260716.md`）と同じ手順で搾取者の牌譜を
読めば、「非鳴き型に対する搾取戦術」という**人間が読める麻雀の知見**として抽出できる
（`mjai_log_to_html.py` が使える）。フリー雀荘で実際に打つ人間にも転用可能。逆に
打ち筋が「普通に上手いだけ」に見えるなら、それも §3d の定量側と突き合わせる定性証拠。

**注意点**:

- **分散の壁**: StarCraft は実力差がほぼ毎試合出るが、麻雀は運の分散が巨大で
  「搾取者が勝ち越している」の検定自体に大量の半荘が要る。卒業判定・PFSP の勝率推定が
  全てこのノイズと戦う
- **コスト**: 搾取者1体 = 本体1本ぶんの訓練 run。リーグを回すのは探索ラダー1段より高い
- **4人ゲームの理論的保証はない**: AlphaStar は実質1v1。4人麻雀では「リーグが均衡に
  収束する」保証は消えて経験的手法になる

→ 現実的な始め方はフルのリーグではなく**搾取者1体だけ**。Stage1-16000 を凍結標的に
1本訓練し、有意にチップを毟れるかだけ見る。

## 4. 候補3: KL 正則化ダイナミクス（R-NaD 系）— 不採用寄り

### 4a. 機構

参照方策 π_reg = 現在の方策の凍結コピーを置き、「正典報酬 − η·KL(π‖π_reg)」を目的に
PPO を回す（参照から離れすぎると罰金）。収束したら π_reg を今の π で置き換えて反復。
アンカーを引きずりながら進む動的均衡化で、狙いはリーグ訓練と同じ**じゃんけんの
堂々巡り防止**。リーグが「過去の戦略を集団として残す」ことで循環を防ぐのに対し、
こちらは「過去の自分への引力」で防ぐ。2人ゼロ和ならナッシュ均衡への収束が証明され、
Stratego（DeepNash）で実証された。人手ゼロ・追加 run ゼロ・PPO 損失に1項足すだけ。

### 4b. なぜ L1/L2 でなく KL か（他の設計判断でも再利用できる論点）

方策 π(·|s) は確率ベクトルなので L2 距離も定義できる。それでも KL が選ばれる理由:

1. **L2 は確率の裾の異変に気づかない — うちの問題は裾に住んでいる**。ある局面で
   カンを P=0.02 で打つ参照方策に対し、新方策がこれを P=0.000001 まで潰した場合:
   L2 的な差は (0.02 − 0.000001)² ≈ 0.0004 でほぼ罰金なし、KL 的な差は
   0.02 × log(0.02/0.000001) ≈ 0.2 で大きい。行動としては「2万分の1に激減 = カンという
   選択肢の事実上の絶滅」なのに L2 は気づかない。KL は確率の**比**（対数スケール）で
   測るので裾の絶滅に悲鳴を上げ、0.51→0.52 のような多数派内の微動はどちらも無視する。
   意思決定では「レアな選択肢が消えるか残るか」こそが質的変化であり、**本プロジェクトの
   3ヶ月は鳴き・カンという低確率行動の絶滅との格闘だった**。正則化に L2 を使うのは、
   守りたいものを一番守れない距離を選ぶことになる
2. **1手単位の制約が半荘単位の制約に化ける**。KL の連鎖則により、各判断での
   KL(π‖π_reg) の合計が半荘全体の牌譜分布のズレの上界になる（L2 にこの合成則はない）
3. **理論の機械が全部 KL 用にできている**。PPO 自体がもともと KL 信頼領域の近似
   （クリッピングは KL 制約の安直な代用品）であり、自然勾配・ミラー降下・後悔最小化・
   R-NaD の収束証明はすべて KL（エントロピー系正則化）を前提に組まれている。L2 に
   替えると「なんとなく前の自分に近い」だけが残り保証は消える

L2 アンカーが爆発するわけではない（漠然とした引力としては機能する）。ただし上の3つを
捨てて得るものが特にない。

### 4c. 不採用の理由（2026-07-25 Gamba 裁定）

本候補の売りは理論保証そのものだが、**4人麻雀では保証が消えるので売りが消える**。
よって優先度は最下位とする。§4b の裾感度の議論のみ、他候補・他の設計判断へ引き継ぐ
（記録目的で本節を残す理由がこれ）。なお `supervisor_handbook.md` §4b「殺した仮説
（再提案禁止）」への登録はしていない — 再提案禁止リスト入りは 0b セッションでの
裁定事項である。

## 5. 候補4: 信念状態つき探索（問題 II の本丸・最も高い）

### 5a. AlphaZero の核と麻雀の壁

完全情報ゲームでの AlphaZero の核は「探索を**方策改善オペレータ**として使う」ループ:
直感 π を案内役に先読みし（読みの結果は直感より必ず少し強い）、**読んだ結果を教師に
直感を訓練する**。自分の熟考を自分の直感に蒸留するので、人間データが要らない。

麻雀の壁は、相手の手牌13枚×3人と山が見えないため**素朴な先読みがそもそも書けない**
こと。「相手の手を適当に1つ決め打ちして読む」には既知の欠陥がある（決め打った世界では
最適でも、あり得る世界の平均では最悪の手を選ぶ等）。

### 5b. 信念状態と1判断あたりの手続き

探索の対象を「盤面」から**「盤面 + 信念」**に差し替える。信念（belief）とは、自分の
観測（自手・全員の捨て牌・鳴き・立直）と整合する隠れ状態（3人の手牌 + 山）全体の
確率分布 — Gamba が「読み」と呼んでいるものの数学的な正体である。手続き:

1. 信念から世界を N 個サンプルする（相手の手と山の割り当てを N 通り作る）
2. 候補行動ごと（鳴く/鳴かない/各打牌）に、各世界で現在の方策ネットで局末まで
   ロールアウトする
3. 行動ごとの平均収益 → その局面での Q(s,a) 推定
4. **この Q を教師に方策ネットを訓練する**（AlphaZero と同じ蒸留）

### 5c. なぜラダー失敗への直撃薬なのか（本書の最重要論点）

探索ラダー3段の失敗の根本原因を一言で言うと、**方策勾配はサンプリングされた行動しか
評価できない**ことである。鳴き確率が裾へ沈む → 鳴きの試行データが枯れる → 鳴きの
価値を再評価する機会自体が消える → 絶滅が固定。ラダー3段（探索量・状態分布・報酬）は
すべて「サンプリングされる確率を人工的に持ち上げる」延命策であり、外すと戻った
（Stage1 0.236× / Stage2 0.185× / Stage3 anneal 後 1.066× で slope/SE=−21.03 の減衰）。

探索ベースは論理が違う。**候補行動は確率ゼロでもロールアウトで明示的に査定される。**
鳴きが方策から絶滅していても、探索は毎判断「もし鳴いたら?」を実際に転がして値を出す。
どこかに鳴きが得な局面が実在するなら探索がそこで高い Q を付け、蒸留で方策に書き戻す
— **探索のための確率を維持する必要がそもそもない**。「サンプリング頼みの探索」を
「列挙による査定」で置き換える、というのが質的な違いである。

### 5d. 既に手元にある部品

- **DRCA はこの探索の手動1点版そのもの**。分岐点で両腕をロールアウトして
  Q(s,鳴く) − Q(s,鳴かない) を測る手続きは §5b の 2–3 と同型で、違いは「訓練ループの
  外で診断として少数やるか」「中で多数やるか」だけ
- **fork-by-replay 基盤**（台本記録・(role, seq) バケット照合による決定論的再生。
  `drca_probe_design.md` §2）が、そのロールアウトエンジンの原型
- **候補1 の oracle 蒸留が信念の学習そのもの**。訓練時はシミュレータが真の隠れ状態を
  知っているので「観測 → oracle 計算した正解」で訓練すると、ネットは自動的に
  「観測と整合する世界たちの平均」= 信念平均を学ぶ。信念モデルを別途設計しなくても
  SGD が周辺化を担う

→ 候補1 と候補4 は独立な選択肢ではなく**同じ坂道の下と上**である（候補1 で信念を
育て、候補4 でその信念の上に探索を載せる）。

### 5e. コストと `drca_probe_design.md` §7 との関係

- **計算量が桁で増える**（1判断 = 世界数 × 候補数のロールアウト）。値引き策は
  「探索は訓練時のみ・全判断でなく抜き取り・浅いロールアウト」
- **実装工数が最大**。ラダー各段が「PPO に1項足す」規模だったのに対し、これは
  訓練ループの構造変更である。Gamba の指摘（2026-07-25）: 商用版は AGPL とデータ事情
  からゼロ実装する方針（README）なので、この最大の障壁は「どうせ払う工賃」に吸収され
  得る。fork-by-replay で最も厄介な決定論的再生の設計知見も既に手元にある
- **理論保証は 2人ゼロ和まで**（ReBeL / Player of Games はポーカーで実証）。ただし
  候補3 と決定的に違う点があり、R-NaD は「ナッシュに収束する」ことが売りの全部だった
  のに対し、**探索の実用価値は均衡収束と無関係に立つ**（「各局面でより良い手を選ぶ」
  というローカルな改善であり、AlphaZero 系が強い理由は保証ではなくこれ）。4人戦で
  保証が消えても売りの本体は残るので、§4c の不採用理由はここには当てはまりにくい

**境界（重要）**: 候補4 のうち「鳴き決定ステップの advantage を paired-rollout 推定で
置換・補正する」部分は `drca_probe_design.md` §7 phase 2 と重なる。同 §7 は**判定
B（∧C）成立時のみ検討を解禁**すると凍結文書に書かれており、**本書はその解禁条件を
緩めない**。また §7 は「新規 Rust 表面（真のフォーク API）が必要になる可能性が高いのは
こちら」と警告している。

## 6. 候補5: HITL（人間 attention 係）— 横断

### 6a. 当初案とその不成立理由

Gamba の当初提案（2026-07-25）: 天鳳牌譜で学習するフェーズを「AI の自己対戦 + Gamba に
よるラベリング」で代替し、後半は現行 PPO で回す。この形では2つの理由で不成立。

1. **ラベル量の桁**: 本家の教師フェーズが学ぶ判断数は数億オーダー（数百万半荘 ×
   1半荘あたり百数十判断）。人間が1日500判断をラベリングしても年間 10^5 程度で
   3–4桁足りない。行動の直接ラベリング（behavioral cloning）は最もラベル効率が悪い
   使い方であり、「教師フェーズの代替」としては物理的に成立しない
2. **より本質的 — Stage3 の人力版である**: 序盤に人間ラベルで方策を形成しても、後半を
   純 PPO（正典報酬のみ）で回すなら、人間由来の事前分布は正典報酬の勾配に支持されない
   限り洗い流される。Stage3 の anneal 付き鳴きボーナスがまさにこの構造で、介入期間中は
   π(鳴き|可能∧赤保持) が 2.475× まで立ち上がったのに、anneal 完了後は
   slope/SE=−21.03 で Stage1 平衡へ回帰した（`ppo_p3_stage3_result.md` §6）。
   **「介入をやめた後に残るのは、報酬が支持する行動だけ」**が探索ラダー3段から得た
   最も硬い知見である

加えてプロジェクト固有の循環がある。人間ラベリングは「人間の麻雀観が正しい」ことを
前提にするが、DRCA でまさに検証しているのは「β=1 チップルールで鳴きが本当に EV 正か」
である。DRCA が「鳴きは本質的に割に合わない」と出れば、人間ラベルは誤った事前分布の
注入になる。

### 6b. 修正版: answer ではなく attention

提案の骨格（方策自身が訪れる状態分布上で人間が介入する）は DAgger 系の考え方であり、
純 BC より理論的に正しい形である。「人間らしさ不要・純 EV 最大化」の目標
（2026-07-25 Gamba 明言）と両立させるには、人間を**教師ではなく仮説生成器**として
使う:

| | 従来案 | 修正案 |
|---|---|---|
| 人間の出力 | 「ここは鳴くべき」という**正解** | 「ここは鳴きも有力では?」という**候補提案** |
| 採否の決定 | 人間（人間が正しい前提） | **反実仮想ロールアウトの実測**（シミュレータが勝った腕を採用） |
| 人間観が誤っていた場合 | 誤った事前分布が注入される | **害がない**（ロールアウトが棄却するだけ） |

- ラベルは全判断ではなく**重要分岐点に絞る**。DRCA の分岐点抽出機構がそのまま使える。
  パイロット定性ドリルダウン（`drca_pilot_qualitative_notes.md`）の branch 15
  「東3・4本場・1向聴のチー機会、ΔQ̂ +18.5 / d_chip +16.25 で全項目中最大、方策は
  パスし親のツモ +21200 を被弾」が取りこぼし候補の実例。数百件で足りる可能性がある
- 人間の役割は answer ではなく **attention**（探索すべき場所と選択肢を指差すだけ）。
  AI が見落としている好機だけが選択的に救われる

### 6c. 他候補との合流点

- **候補4 と合流**: 候補4 の値引き策「全判断でなく抜き取り探索」の抽出箇所を人間が
  指差す形になる（§5e）
- **用済みになった派生案**: 当初案の系列には「注入した事前分布を anneal で消さず
  KL(π‖π_human) として恒久的に残す」案もあったが、これは配備方策を人間事前分布に
  恒久的に制約する = 人間らしさを製品仕様とみなす場合のみ正当化される。人間らしさを
  目標から外した 2026-07-25 の Gamba 明言により**用済み**として記録する
