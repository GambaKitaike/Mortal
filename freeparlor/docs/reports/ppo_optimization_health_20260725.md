## 0. 結論（3行）

1. **1 optimizer step の実効サンプル数は中央値 168–179**（`minibatch_size=512` は
   **全 run・全バッチで一度も効いていない**）。実体は「1 半荘の full-batch × 4 epochs」。
2. **バッチ到着時点で既に clip_fraction ≈ 0.20–0.33**。原因は client/trainer 間の
   パラメータ非対称（`logp_old` は client が行動時に記録）で、定常的に
   **50–100 optimizer step 分の staleness** が乗っている。陽性対照
   （`trainer_step=0`、client と trainer が同一パラメータ）では **clip = 0.0000**。
3. **4 epochs は trust region 占有をほとんど動かさない**（epoch1→epoch4 の clip 差は
   全 run で **−0.0008 〜 −0.0032**）。つまり clip は「この更新の行き過ぎを抑える」機能を
   果たしておらず、**収集経験の約2割を恒常的に勾配から除外している**。

**いずれも 8 run 全てに共通**で、anchor_c 固有ではない（§1 の横断表）。
**因果は本書では主張しない**（§5 の限界を参照）。

## 2. [A] batch_size — `minibatch_size = 512` は一度も効いていない

全 run で `batch_size` の分布は median 168–179 / max 347–412 / min 9–30。
**512 を超えたバッチは 0.00%**（`stage1_20260705_053301` を含め max が 512 未満）。

構造上の理由（コード確認済み・バグではなく設計の帰結）:

- 1 optimizer step = 1 `.traj` ファイル = **1 半荘**（`mortal/train_ppo.py:624-628`, `:574`）。
- `mb_size = minibatch_size if minibatch_size < n else n`（`train_ppo.py:465`）なので
  n（1半荘の decision step 数）が 512 未満である限り**ミニバッチ分割は起きない**。
- 複数半荘をまとめる経路が存在しない: `collate_trajectory_batches`
  （`mortal/ppo_dataloader.py:44`）は `train_ppo.py:36` で import されているが
  **どこからも呼ばれていない（デッドインポート）**。

**帰結**: advantage の z-score 正規化（`mortal/ppo.py:105`, `:41-44`）は
**~170 サンプルの標本統計**で行われる。しかも報酬は局末 step のみ非ゼロ
（`ppo_dataloader.py:26-36`）なので、1 バッチ内の非ゼロ報酬は局数分（~8）しかない。

## 3. [B] clip_fraction — trust region は「学習」ではなく staleness で消費されている

### 3a. 陽性対照

`trainer_step = 0` では **clip_fraction = 0.0000**（`ratio_mean ≈ 0.99996`,
`ratio_std ≈ 0.0006`）。step 0 では client と trainer のパラメータが同一なので、
ratio ≈ 1 になり clipping は起きない。**測定系は正しく 0 を出せる**。

### 3b. 定常状態の staleness は 50–100 optimizer step

`batch_lag.lag`（client の `param_version` と trainer の差）の分布は全 run で同形:

| run | lag=0 | lag=1 | lag=2 | lag=3 |
|---|---:|---:|---:|---:|
| stage1_20260706_020120_resume | 1.0% | 64.0% | 35.0% | — |
| stage2_20260709_194510_resume | 0.7% | 63.9% | 35.3% | 0.1% |
| stage3_20260712_033403 | 0.8% | 63.7% | 35.4% | 0.2% |
| anchor_c_20260725_164756 | 1.4% | 56.4% | 41.9% | 0.3% |

`submit_every = 50` なので **lag 1 単位 = 50 optimizer step**。lag=0 は最初の
param_version 窓（step 0–49、client がまだ一度も更新を受け取っていない区間）にほぼ限定され、
**定常状態は lag 1–2 = 50–100 step のドリフト**。

⚠ **`lag` は staleness の代理変数としては粗い**（param_version 単位なので lag=0 でも
窓内で最大 49 step のドリフトを含む）。実際 `stage1_20260705_014852` の lag=0 群は
clip 平均 0.31、`anchor_c` の lag=0 群は 0.366 と**定常値より高い** — これは step 0–49 の
区間で学習率が最も効き、frozen な client スナップショットから trainer が急速に離れるため。
lag の値そのものではなく**分布（1–2 が支配）**を読むのが正しい。

### 3c. epoch を重ねても clip は増えない

`stage3_20260712_033403`（完走 16000 step、n=16000 バッチ）の例。他 run も同形:

| epoch | clip mean | clip median | ratio_std mean |
|---|---:|---:|---:|
| 1 | 0.2151 | 0.2067 | 0.2059 |
| 2 | 0.2148 | 0.2061 | 0.2054 |
| 3 | 0.2142 | 0.2053 | 0.2045 |
| 4 | 0.2138 | 0.2053 | 0.2035 |

**epoch1 → epoch4 の差は全 run で −0.0008 〜 −0.0032**（符号は一貫して負）。
`ratio_std` も増えない。

**読み**: バッチに勾配を当てる**前**（epoch 1）に既に ~22% が trust region の外にあり、
4 epochs の更新はその占有率をほとんど動かさない。つまり:

- clip は設計上の役割（**この**更新が方策を動かし過ぎるのを抑える）を果たしていない。
  ratio のずれは更新の帰結ではなく、バッチに最初から乗っている固定オフセットである。
- clip された ~2割のサンプルは（advantage の符号次第で）勾配 0 になる。
  **収集した経験の約2割が恒常的に学習に寄与していない。**
- `lr = 2e-5` × ~170 サンプルの 1 epoch の更新量は、この staleness オフセットより小さい。
  **4 epochs は計算を 4 倍払って trust region 占有を 0.3% 動かす取引になっている。**

## 4. [E] advantage のカテゴリ別サンプル数

`advantage_decomp` の各カテゴリの n（バッチごと・median）:

| run | call_taken | call_declined | riichi_taken | riichi_declined |
|---|---:|---:|---:|---:|
| stage1_20260706_020120_resume | 2 | 30 | 3 | 1 |
| stage2_20260709_194510_resume | 2 | 30 | 3 | 1 |
| stage3_20260712_033403 | 12 | 19 | 2 | 1 |
| anchor_c_20260725_164756 | 6 | 28 | 2 | 2 |

加えて「そのバッチに該当決定が存在しない」回数が大きい（例 stage3 の
`riichi_declined` は 16000 バッチ中 **14456 バッチで不在**、stage1 final の
`call_taken` は 6000 バッチ中 1395 バッチで不在）。

**読みの限定（重要）**: これは **Stage1/Stage3 判定で報告された advantage 値
（call_taken +0.018 / declined +0.522 等）が信用できない、という主張ではない**。
判定値は判定窓の数千バッチにわたる集計なので、集計値としては問題ない。
本節が指すのは**1 回の勾配更新が乗るサンプル数**であり、
「~170 サンプル中、鳴き選択は数個」という per-update の分散構造である。

## 5. 限界（本書が主張しないこと）

- **因果を主張しない。** §2–§4 はいずれも「設計上そうなっている」ことの実測であり、
  これが `fundamentals_degradation_diagnosis_20260725.md` §3 の基礎劣化
  （放銃 z +3.9〜+4.4）の**原因である証拠は本書には無い**。L1 は診断 §4 の仮説序列に
  載っていない第4の候補として**追加**されるべきだが、序列を書き換える根拠はまだない。
- **anchor 系列の判定には関与しない。** Arm C/K の判定条件（`anchored_ppo_design.md` §6）は
  凍結済みで、本書はそれに触れない。効くのは**判定の解釈**の側だけ
  （「C も K も効かなかった」場合に L1 由来の可能性を排除できない、という留保）。
- **診断 §4 が挙げていない他の候補**（entropy 係数、value ヘッド初期化、行動空間の偏り）は
  本書でも未検証。`ppo_diag.jsonl` に entropy / explained_variance が出ていないため
  既存データでは測れない（`explained_variance` は `train_ppo.py:516-518` の変数上書きにより
  最後のミニバッチの値しか残らず、そもそも診断ログに出ていない）。
- **改善案は本書に書かない。** 対策の設計は
  `freeparlor/docs/design/robust_selfplay_ppo_design.md`（DRAFT）に分離した。

## 6. 副産物: 版採番の不整合（1 run・情報として記録）

`stage1_20260705_053301` の **240/11990 バッチ（2.00%）で `lag < 0`**
（client の `param_version` が trainer より新しい）。範囲は **step 10000–10239** に限定、
値は −235 / −234 / −233。

- **解釈**: step 10000 は resume 境界であり、trainer 側の `param_version` 採番が
  1 にリセットされた一方 client が resume 前の版（235 以降）を保持していた、と読める。
- **判定への影響なし**: この run は Stage1 の判定に用いた run ではない
  （判定は `stage1_20260706_020120_resume` の step16000）。他の 7 run では `lag < 0` は 0 件。
- **含意**: `lag` を診断指標として使う場合、resume を挟んだ run では版採番の連続性を
  確認する必要がある。スクリプトは該当時に WARNING を出す。
